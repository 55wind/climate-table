# 밥상 차리기 — 인터랙티브 밥상 시뮬레이션 (설계)

작성일: 2026-06-26
대상 프로젝트: 기후 식탁 (Climate Table) — 기상·기후 AI 해커톤 출품작

## 1. 배경 & 목표

기존 시뮬레이션 탭은 작물 1종의 날씨→가격 변화를 보여준다. 추상적 % 변화는
체감이 약하다. **"이 기후에서 내 밥상이 얼마가 되는가"**를 직접 차려 보며 느끼게
하는 새 탭을 추가한다.

사용자가 음식(요리)을 **드래그&드롭으로 식탁에 올리면**, 각 음식의 재료(원자재)에
대해 날씨에 따른 물가상승률을 계산해 **밥상 총액 · 평년 대비 % · 재료비 분해**를
보여준다.

기존 시뮬레이션·퀴즈 탭은 그대로 둔다(비파괴적 추가).

## 2. 핵심 결정 (확정)

- **탭 추가**: 상단 탭이 `시뮬레이션 · 밥상 차리기 · 학습 퀴즈` 3개가 된다.
- **날씨 시나리오 공유**: 기존 `state.scenario`(폭염일수·가뭄지수·월 등)를 그대로
  사용한다. 밥상 탭에는 현재 적용 중인 날씨 요약 배지 + 빠른 프리셋 버튼만 두고,
  세부 슬라이더는 기존 탭에 둔다. 같은 기후 조건에서 밥상이 어떻게 변하는지 본다.
- **가격 구성 = 현실 총액**: 기후 민감 작물 6종은 모델로 날씨를 반영하고,
  고기·두부·양념 등 비기후 재료는 고정가로 더해 "실제 장바구니 총액"에 가깝게 한다.
- **레이아웃 = 식탁 중심형(A)**: 위 음식 트레이 / 가운데 큰 식탁(드롭 영역) / 아래
  결과 패널.
- **이미지 = 3D·클레이 일러스트**: 음식·식탁 모두 투명배경 무료 라이선스 에셋을
  로컬 번들. 통일된 스타일로 "AI slop" 인상을 피한다. (기존 "CDN 의존 0" 유지)
- **백엔드 신규 엔드포인트**: 레시피·가격 로직을 백엔드에 두어 테스트 가능하게 한다.

## 3. 모델: 음식 ↔ 재료

기후 모델이 다루는 작물은 6종뿐이다: **배추·무·사과·쌀·시금치·양파**.
각 음식은 1인분 기준으로 두 종류의 재료로 구성한다.

- **기후 재료(crop)**: 6종 중 하나. `amount_kg`(분량) 보유. 가격 = 작물 예측가(원/kg)
  × `amount_kg`. 예측가는 현재 날씨 시나리오로 계산.
- **고정 재료(fixed)**: 고기·두부·양념 등. `won`(정가) 보유. 날씨와 무관.

재료비 환산은 기존 앱과 통일한다: **예측 도매가(원/kg) × 분량(kg)**. (별도 소매
마진은 적용하지 않음 — 기존 `UNIT_PACK` 환산과 동일한 관례.)

### 음식 카탈로그 (초안 8종, 1인분)

| id | 이름 | 기후 재료 (작물·kg) | 고정 재료 (원) |
|---|---|---|---|

| `kimchi_jjigae` | 김치찌개 | 배추 0.12 · 양파 0.05 · 무 0.03 | 돼지고기 2500 · 두부 900 · 양념 400 |
| `doenjang_jjigae` | 된장찌개 | 양파 0.05 · 무 0.05 · 시금치 0.02 | 두부 900 · 된장양념 500 |
| `baechu_kimchi` | 배추김치 | 배추 0.18 · 무 0.04 · 양파 0.03 · 사과 0.02 | 고춧가루·젓갈 800 |
| `mu_saengchae` | 무생채 | 무 0.12 · 양파 0.02 · 사과 0.02 | 양념 300 |

- 분량·정가는 교육용 근사값이며 구현 시 한 곳(데이터)에서 조정 가능하게 둔다.

## 4. 아키텍처 & 데이터 흐름

### 백엔드 (Python 표준 라이브러리, 기존 패턴 유지)

레시피·정가 데이터를 백엔드 모듈로 분리한다: `backend/dishes.py`
- `DISHES`: 위 카탈로그(id·이름·이미지 파일명·재료 목록).
- 순수 데이터 + 조회 함수만. 모델 의존 없음(가격 계산은 app.py가 MODEL로 수행).

`backend/app.py`에 엔드포인트 2개 추가:

**`GET /api/dishes`**
```json
{ "dishes": [
  { "id":"kimchi_jjigae", "name":"김치찌개", "img":"kimchi_jjigae.png",
    "ingredients":[
      {"name":"배추","kind":"crop","crop":"배추","amount_kg":0.12},
      {"name":"돼지고기","kind":"fixed","won":2500} ] } ] }
```

**`POST /api/meal`**
요청: `{ "scenario": {"heat_days":28, ...}, "month": 8, "dishes": ["rice","kimchi_jjigae", ...] }`
- 작물별로 `MODEL.predict(crop, scenario, month)`(예측)와
  `MODEL.predict(crop, BASELINE, month)`(같은 시기 평년 기상)을 한 번씩 계산해 캐시.
- 각 음식·재료의 예측가/평년가를 분량으로 환산, 고정 재료는 양쪽에 동일 가산.
응답:
```json
{
  "total": {"predicted": 18400, "baseline": 15000, "pct": 23},
  "dishes": [
    {"id":"kimchi_jjigae","name":"김치찌개","predicted":4200,"baseline":3600,"pct":17,
     "ingredients":[{"name":"배추","kind":"crop","predicted":340,"baseline":240,"pct":42}, ...]}
  ],
  "ingredientTotals": [
    {"crop":"배추","predicted":900,"baseline":620,"pct":45,"usedIn":["김치찌개","배추김치"]}
  ]
}
```
- `pct`는 평년 대비 상승률(반올림). 고정 재료는 predicted=baseline이라 음식 pct를
  희석한다(현실적). `ingredientTotals`는 기후 작물만 집계해 "어떤 원자재가 밥상값을
  올렸나"를 보여준다.

**대안(비채택)**: 프론트가 `/api/simulate`를 작물별로 호출해 합산. 백엔드 무수정이나
레시피가 JS에 흩어지고 테스트가 어려워 비채택.

### 프론트엔드 (frontend/app.js, 기존 IIFE 내 확장)

- 초기화 시 `GET /api/dishes` 1회 호출, 카탈로그 캐시.
- 탭 전환 로직(`setupTabs`)을 2탭 → 3탭으로 확장.
- 밥상 상태: `state.meal = []`(식탁에 올린 음식 id 목록, 중복 허용).
- 변경(드롭/제거/프리셋) 시 디바운스 후 `POST /api/meal` → 결과 렌더.
- 기존 시뮬과 동일하게 `state.scenario` 변경 시에도 밥상 탭이 열려 있으면 갱신.

#### 모듈 경계 (단일 책임)
- `buildTray()` — 트레이 음식 카드 렌더 + 드래그 시작 바인딩.
- `setupTable()` — 식탁 드롭 영역(dragover/drop), 음식 배치/제거.
- `renderMeal(res)` — 총액·음식별·재료 분해 렌더.
- `simulateMeal()` — 디바운스 → `/api/meal` 호출.

## 5. 인터랙션 (드래그&드롭)

- **데스크톱**: HTML5 Drag and Drop. 트레이 카드 `draggable=true` →
  식탁 드롭 영역에 `drop` 시 해당 위치(자유 배치)에 음식 접시 추가.
- **모바일/폴백**: 카드 **탭**으로도 식탁에 추가(드래그 어려운 환경 대비).
- 식탁 위 음식 **클릭/탭 시 제거**. "비우기" 버튼으로 전체 초기화.
- 접시는 식탁 PNG 위 절대 위치. 겹침은 드롭 좌표 + 소량 오프셋으로 분산(복잡한
  물리 분리 불필요 — 자유 배치).

## 6. 결과 패널

- **밥상 총액**(원) + **평년 대비 %** 배지(상승=강조).
- **음식별 미니 카드**: 이름 · 가격 · 평년比.
- **재료비 분해(원자재)**: `ingredientTotals`를 막대로. 상승 기여가 큰 작물 강조 →
  "배추 +45%가 오늘 밥상값을 끌어올렸습니다" 식의 한 줄 인사이트.
- 빈 밥상일 때: 안내 문구("음식을 식탁에 올려 보세요").

## 7. 이미지 / 에셋

- 디렉터리: `frontend/assets/foods/<id>.png`, `frontend/assets/table.png`.
- 3D·클레이 일러스트, 투명배경, 무료 라이선스(예: Flaticon 3D / Icons8 무료 등).
- 출처·라이선스·URL을 `frontend/assets/CREDITS.md`에 기록(라이선스 준수).
- 백엔드 정적 서빙(`_static`)은 `.png`를 이미 지원. `assets/` 경로도 그대로 서빙됨.
- **폴백**: 이미지 로드 실패(`onerror`) 시 음식별 이모지로 대체해 항상 동작.

## 8. 에러 처리 & 엣지 케이스

- `/api/dishes` 실패 → 토스트 안내, 밥상 탭은 안내 문구만.
- `/api/meal` 빈 목록 → `total {0,0,0}`, "밥상이 비었습니다".
- 알 수 없는 음식 id → 백엔드가 무시(스킵)하고 유효한 것만 계산.
- 작물 분량 0/음수 방어, 정가 음수 방어.
- 같은 음식 여러 번 담기 허용(수량 개념).

## 9. 검증 (test_api.py 확장)

- `GET /api/dishes`: 8종 반환, 각 음식 재료 구조 유효(crop은 6종 내, fixed는 won>0).
- `POST /api/meal`:
  - 정상 시나리오에서 total.predicted ≥ baseline(상승 시나리오) 합산 검증.
  - 빈 밥상 → 0 반환.
  - 알 수 없는 id 섞여도 200 + 유효분만 계산.
  - 평년 시나리오(BASELINE) → pct ≈ 0.
- 회귀: 기존 18개 테스트 영향 없음 확인.

## 10. 범위 밖 (YAGNI)

- 저장/공유, 영수증 PDF, 수량 스텝퍼 UI(중복 담기로 충분), 다국어, 애니메이션 물리.
- 소매 마진·지역별 가격(기존 앱 관례 유지).
